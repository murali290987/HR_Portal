# HR RAG Assistant

A minimal, from-scratch Retrieval-Augmented Generation (RAG) pipeline over
a small set of sample HR documents — built as a hands-on learning project
covering chunking, embeddings, vector search, grounded generation,
access control, and a basic RBAC extension, with no RAG framework
(LangChain/LlamaIndex) in the way.

## What it does

Ask an HR question in plain English (via CLI or the included web UI) and
get an answer grounded in the actual sample documents in `hr_docs/` —
not the LLM's own memorized knowledge. Two of those documents are a
specific employee's confidential offer letter and appraisal letter; the
rest are general company policies. The pipeline enforces who can see
what, based on a simulated logged-in identity and role.

## How it works

```
hr_docs/*.md
     │  chunk (fixed-size, overlapping windows)
     ▼
ingest.py ──► embed each chunk (all-MiniLM-L6-v2, 384-dim vectors)
     │
     ▼
faiss_index.bin (vectors)  +  chunks_metadata.json (text + metadata)
     │
     ▼
query.py / server.py
     │  embed the question with the same model
     │  ask FAISS for the nearest chunk vectors
     │  drop chunks the requester isn't allowed to see (access control)
     │  drop chunks that don't match an employee ID named in the question
     │  build a prompt: "answer using ONLY this context"
     ▼
LLM (Claude or a local Ollama model) ──► grounded answer
```

### Access control & RBAC

Every chunk carries `doc_type` (`"general"` or `"personal"`) and
`employee_id` metadata from ingestion. At query time:

- An **`employee`** role can only see their own personal documents —
  general policy docs are visible to everyone.
- An **`hr`** role bypasses the ownership check and can see any
  employee's personal documents.
- A separate **relevance guardrail** catches a specific failure mode:
  if the question names a specific employee ID (e.g. `EMP99999`) and
  nothing retrieved actually belongs to that ID, the LLM is never
  called — a fixed "I don't have relevant information" message is
  returned instead. This exists because a small local model, given
  context about the *wrong* employee, would otherwise misattribute
  that employee's data to whoever the question named.

None of this is real authentication — see **Known limitations** below.

## Project structure

```
hr_rag/
├── hr_docs/              8 sample markdown docs (6 general, 2 personal)
├── config.py             all tunable constants (chunk size, models, users/roles, ...)
├── ingest.py             chunking + embedding + FAISS index build (run this first)
├── query.py              CLI: retrieval + access control + generation
├── server.py             FastAPI wrapper around query.py, for the web UI
├── web/                  React (Vite) frontend — chat UI with a retrieval trace view
├── evals/                golden-dataset eval harness (see Evaluation below)
├── requirements.txt
├── .env.example          copy to .env and add your ANTHROPIC_API_KEY
└── faiss_index.bin, chunks_metadata.json   generated by ingest.py (gitignored)
```

## Setup

```bash
cd hr_rag
python3 -m venv .venv
./.venv/bin/pip install -r requirements.txt

# Build the FAISS index from hr_docs/ (only needs re-running if hr_docs/ or config.py's
# chunking/embedding settings change)
./.venv/bin/python3 ingest.py
```

Pick an LLM provider in `config.py` (`LLM_PROVIDER = "anthropic"` or
`"ollama"`):

- **Anthropic**: copy `.env.example` to `.env` and set `ANTHROPIC_API_KEY`.
- **Ollama**: install [Ollama](https://ollama.com), run `ollama pull llama3.1:8b`
  (or update `OLLAMA_MODEL` in `config.py` to whatever you've pulled).

## Usage

**CLI:**

```bash
./.venv/bin/python3 query.py "How many casual leaves do I get per year?"
```

Prints the retrieved chunks (with similarity distance + metadata) and
the final answer. Change `CURRENT_USER_ID` in `config.py` to any key in
`USERS` to test access control as a different identity/role.

**Web UI** (chat interface with a live retrieval trace, and dropdowns to
switch identity/role and LLM provider):

```bash
# Terminal 1
./.venv/bin/python3 -m uvicorn server:app --port 8000

# Terminal 2
cd web && npm install && npm run dev
```

Then open http://localhost:5173.

## Configuration

Everything tunable lives in `config.py`: chunk size/overlap, `TOP_K`,
the embedding model, `LLM_PROVIDER` and per-provider model names, and
`USERS` (id → role) for the access-control simulation.

## Evaluation

`evals/` holds a golden-dataset eval harness — a way to measure whether
a change (chunk size, top_k, prompt wording) actually helped, instead of
eyeballing a handful of queries. Full details, including how to read
every metric and two documented weaknesses in the answer-quality
checks, are in **[`evals/README.md`](evals/README.md)**. Summary:

- **`dataset.py`** — 21 hand-built cases across 7 categories, grounded
  in `hr_docs/`'s actual content. Two cases are deliberately marked
  `known_limitation: True` — both stem from the same root gap (the
  relevance guardrail's `EMP\d+` regex only catches an explicit
  employee ID, never a name or a bare pronoun), reached via two
  different paths: an owner naming a different person by name, and the
  `hr` role's blanket bypass answering a vague "my ..." question with
  someone else's data. Measured on every run, not silently patched away.
- **`run_retrieval_eval.py`** — fast, no LLM calls: hit@k, precision@k,
  recall, leak count, guardrail accuracy against the real
  `query.retrieve()`/`apply_relevance_guardrail()`.
- **`sweep.py`** — the same eval across a grid of
  `CHUNK_SIZE`×`CHUNK_OVERLAP`×`TOP_K`, each re-ingested into a
  throwaway temp directory (your real index is never touched).
- **`run_answer_eval.py`** — the slow one: runs full generation and
  checks answer content, run on demand with `--provider ollama` or
  `--provider anthropic`.
- **`test_regressions.py`** — pytest wrapper; fails the build on any
  leak or a hit@k regression below one floor constant.

```bash
./.venv/bin/python3 evals/run_retrieval_eval.py     # run this often
./.venv/bin/python3 -m pytest evals/test_regressions.py -v -s
```

## Known limitations

This is a learning project, not a production system:

- **No real authentication.** `CURRENT_USER_ID`/`USERS` are hardcoded
  stand-ins for a verified session (e.g. a signed JWT). Anyone editing
  `config.py`, or the API's `user_id` field, can claim any identity —
  the *role* for that identity is still resolved server-side and can't
  be spoofed by the client, but the identity itself isn't verified at all.
- **Fixed-size chunking** splits text by raw character count, not by
  sentence/paragraph/heading — it can (and does) cut sentences and
  table rows in half.
- **No universal "is this relevant" threshold.** An embedding-distance
  cutoff was tried and abandoned — with a corpus this small and a
  lightweight embedding model, genuinely relevant and irrelevant matches
  land in overlapping distance ranges. Only the narrow employee-ID
  mismatch guardrail is deterministic; the general "nothing here
  answers this" case still depends on the LLM's own judgment.
- **The relevance guardrail only catches an explicit `EMP\d+` pattern,
  not a name or a bare pronoun.** Two tracked, reproducible ways this
  shows up (both in `evals/dataset.py`, both intentionally left unfixed
  rather than patched silently):
  - `known_limitation_name_bypass` — a requester asks about a different
    identity by *name* instead of ID; their own real personal data gets
    retrieved and risks misattribution by the LLM.
  - `known_limitation_hr_first_person_bypass` — the `hr` role's
    ownership bypass plus a vague first-person question ("what is my
    name?") with no name or ID at all; the closest personal chunk in
    the whole corpus gets returned and answered as if it were the
    requester's own. Confirmed live: HR001 asking "what is my name"
    got back "Priya Ramanathan."
- **Small local models can misphrase or over-hedge**, even when
  retrieval and access control are working correctly.
